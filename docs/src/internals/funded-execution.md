# Funded execution and node admission

`[admission]` enables a single node owner for all physical create, resume, snapshot restore and fork operations. The scheduler's heartbeat reports are placement hints; they never reserve resident memory. The node atomically reserves startup slots, memory and disk before it prepares or executes a guest. The admission owner requires cgroup v2 metering and Linux pidfds. It refuses startup while an unreaped runtime remains in its delegated cgroups.

Each Sandbox has equal `cpu.weight` and a `cpu.max` ceiling equal to its visible vCPU count. Its initial resident budget defaults to 4 GiB and grows when usage reaches half of the budget. The sum of hard limits stays within 85% of effective host/container memory; live host and ancestor-cgroup headroom also bound new reservations and growth. Memory above the admitted budget can cause a Sandbox-local OOM. Guest addressable memory is a burst ceiling, not guaranteed resident memory. Swap is disabled. Disk admission conservatively reserves the writable ceiling and an uncompressed checkpoint for the admitted resident budget, with an additional node reserve. These conservative reservations can limit density before CPU does.

Set `require_execution_lease = true` when every execution must have funding. The authoritative wire contract is `ExecutionLease` in `src/api/openapi.yml`: activation and operation UUIDs, a monotonic sequence, and an absolute UTC millisecond deadline. A fresh physical activation uses sequence zero. A funded create/fork uses its activation UUID as its Sandbox ID; resume retains the Sandbox ID and starts a new usage instance under its new activation UUID. Renewals must identify the same activation and have a higher sequence, or replay the exact same payload. An expired instance cannot be renewed. Node-local activation tombstones use synchronous LocalKvStore persistence. The control plane must also durably claim each outbound activation once before sending it; node-local tombstones do not fence duplicate dispatches to different nodes.

Before guest execution, the server starts a separate watchdog process holding a pidfd for the exact Firecracker process. The watchdog stops that process on deadline expiry or loss of its private control channel. An independent timer thread enforces the cutoff even if the API server is stopped or a renewal frame is incomplete. Absolute and monotonic deadlines jointly prevent a backward clock adjustment from extending execution. Renewal adds at most the change in the absolute funded deadline. Watchdog control I/O does not hold the node capacity lock. Server or runtime failure may discard unsnapshotted work; stopped runtimes are deleted rather than advertised as recoverable paused snapshots.

`GET /sandboxes/{id}/usage?runtimeInstanceID=...` samples immediately and returns only that activation. The meter fences delayed reads across resume and retains previous final instances through the configured retention period. The heartbeat routing roster retains deleted IDs for that same period so the gateway can still reach their final meters; running/resource counts use lifecycle metadata. A failed cgroup read never freshens an old reading. Final usage is node-local memory; loss of the node before durable collection must remain unresolved in the billing owner, not become zero usage.

Standalone AgentENV users may keep admission or required funding disabled. This is the supported non-billing consumer, not an alternate path for a funded Cloud deployment. Enabling required funding blocks automatic resume without a new caller-issued activation. Active-workload interruption, fairness, pressure behavior and practical density still require Linux/KVM workload validation.

`cargo test -p runtime-policy` covers policy arithmetic and Linux process enforcement, including API-owner SIGSTOP and partial renewal frames. Production acceptance must additionally exercise the actual Firecracker and cgroup paths in an isolated Kubernetes namespace, capture immutable source/image evidence, and remove its resources.
