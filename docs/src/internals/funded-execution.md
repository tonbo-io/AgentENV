# Funded execution and node admission

`[admission]` enables a single node owner for all physical create, resume, snapshot restore and fork operations. The scheduler's heartbeat reports are placement hints; they never reserve resident memory. The node atomically reserves startup slots, memory and disk before it prepares or executes a guest. The admission owner requires cgroup v2 metering and Linux pidfds. It refuses startup while an unreaped runtime remains in its delegated cgroups.

Each Sandbox has equal `cpu.weight` and a `cpu.max` ceiling equal to its visible vCPU count. Its initial resident budget defaults to 4 GiB and grows when usage reaches half of the budget. Early growth does not impose a soft throttle below the admitted hard limit: `memory.high` remains `max`, so a guest can use its whole reserved budget even when further growth is denied. The sum of hard limits stays within 85% of effective host/container memory; live host and ancestor-cgroup headroom also bound new reservations and growth. Memory above the admitted budget can cause a Sandbox-local OOM. Guest addressable memory is a burst ceiling, not guaranteed resident memory. Swap is disabled. Disk admission conservatively reserves the writable ceiling and an uncompressed checkpoint for the admitted resident budget, with an additional node reserve. Before writing a memory checkpoint, the same ledger expands its disk reservation to cover the actual dirty ranges plus format overhead; reclaimed dirty history may be larger than current RSS. Checkpoints must use the admitted runtime filesystem. These conservative reservations can limit density before CPU does.

Set `require_execution_lease = true` when every execution must have funding. The authoritative wire contract is `ExecutionLease` in `src/api/openapi.yml`: activation and operation UUIDs, a monotonic sequence, and an absolute UTC millisecond deadline. A fresh physical activation uses sequence zero. A funded create/fork uses its activation UUID as its Sandbox ID; resume retains the Sandbox ID and starts a new usage instance under its new activation UUID. Renewals must identify the same activation and have a higher sequence, or replay the exact same payload. An expired instance cannot be renewed. Node-local activation tombstones use synchronous LocalKvStore persistence. The control plane must also durably claim each outbound activation once before sending it; node-local tombstones do not fence duplicate dispatches to different nodes.

Before guest execution, the server starts a separate watchdog process holding a pidfd for the exact Firecracker process. The watchdog stops that process on deadline expiry or loss of its private control channel. An independent timer thread enforces the cutoff even if the API server is stopped or a renewal frame is incomplete. Absolute and monotonic deadlines jointly prevent a backward clock adjustment from extending execution. Renewal adds at most the change in the absolute funded deadline. Watchdog control I/O does not hold the node capacity lock. Server or runtime failure may discard unsnapshotted work; stopped runtimes are deleted rather than advertised as recoverable paused snapshots.

`GET /sandboxes/{id}/usage?runtimeInstanceID=...` samples immediately and returns only that activation. The meter fences delayed reads across resume and retains previous final instances through the configured retention period. The heartbeat routing roster retains deleted IDs for that same period so the gateway can still reach their final meters; running/resource counts use lifecycle metadata. A failed cgroup read never freshens an old reading. Final usage is node-local memory; loss of the node before durable collection must remain unresolved in the billing owner, not become zero usage.

Standalone AgentENV users may keep admission or required funding disabled. This is the supported non-billing consumer, not an alternate path for a funded Cloud deployment. Enabling required funding blocks automatic resume without a new caller-issued activation. Active-workload interruption, fairness, pressure behavior and practical density still require Linux/KVM workload validation.

`cargo test -p runtime-policy` covers policy arithmetic and Linux process enforcement, including API-owner SIGSTOP and partial renewal frames. Production acceptance must additionally exercise the actual Firecracker and cgroup paths in an isolated Kubernetes namespace, capture immutable source/image evidence, and remove its resources.

The gateway routes usage reads through the Sandbox owner lookup, including reads of retained final meters. It preserves the `runtimeInstanceID` query fence and never schedules a usage request onto a new node. This matters with multiple nodes: a successful activation on one node does not create a meter on another.


### Proxy route activation ownership

A published runtime route records the funded activation from the final launch, resume or fork metadata along with its guest interaction address. Lease rollover does not replace that activation. `proxy_lookup_for_activation` observes only the exact published activation: missing routes, nil identities and old activations fail without reading a newer metadata record or implicitly resuming a paused VM. Standalone unfunded runtimes retain an explicit absent activation.

The HTTP/WebSocket proxy requires the OpenAPI `ExecutionProxyTargetHeader` JSON target for funded routes. The activation is the fence: the proxy resolves only the exact published activation the caller names. A caller that projected a placement may also pin the `node` target, which reuses `NodeLaunchTarget` validation for node, cluster and service incarnation; callers whose placement authority lives outside the node, such as the Cloud SQL orchestrator, omit it. Missing or stale targets cannot enter a funded guest. Targeted requests never auto-resume, and unfenced requests cannot auto-resume funded paused metadata. The internal header is removed before forwarding to guest services. Standalone unfunded SDK routes retain their existing lookup and auto-resume behavior.

Each route publication owns a transport registry. HTTP and WebSocket connections register with that registry before use; route withdrawal denies new connects, shuts down registered sockets even when response bodies or upgraded streams are not being polled, and waits for pending connect ownership to be released. Pause, deletion and failed-launch cleanup wait before the backend operation. Shutdown failures retain their control descriptors and prevent acknowledgement; retries do not reopen the route. Rollback publishes a fresh registry rather than reactivating old resolved targets. A replacement retains its predecessor registries until all earlier connection obligations are acknowledged. New connects wait for that chain before opening a socket; retiring the replacement also waits for the inherited obligations. Completed chains are released.

Cloud SQL orchestrator, guest-process and ingress consumers must adopt this wire contract before deploying the changed receiver to serving nodes. Full integration and physical address-reuse acceptance, full CR/Node UID placement projection and serving cutover remain pending. Transport unit tests alone do not establish these end-to-end guarantees.
